# 要件定義（たたき台）

最終更新：2026-10-21

## 背景

マンホールカードは、下水道広報プラットホーム（GKP）と自治体が発行するコレクションカードである。
カードごとに決まった配布場所でしか受け取れないため、コレクターは配布場所を地図で探しながら巡る。

既存のマンホールカードのマップは、スマホで外出先から使うことを前提に作られていない。
レスポンシブ対応が不十分で画面が操作しづらく、起動も遅い。
そのため、使ってみたいと思える出来になっていない。

## 目的

外出先のスマホで、開いた瞬間から迷わず使えるマンホールカードのマップを提供する。
他のコレクターにも公開するサービスとして運営する。

## 対象ユーザー

- **マンホールカードのコレクター**：外出先や旅行の計画中に、スマホでカードを探す人。
- **これから集め始める人**：近くでもらえるカードがあるかを気軽に調べたい人。

## 主なユースケース

1. 今いる場所の近くで、もらえるカードを探す。
2. 次の旅行先の地域で、どのカードをもらえるかを調べ、回る計画を立てる。
3. カードを選んで、配布場所、配布時間、蓋の位置を確認する。
4. 回収したカードを記録し、残りの枚数を把握する。
5. ChatGPT などの AI アシスタントに「今度ここへ旅行するが、どのカードを回ればよいか」と相談する。

## スコープ

段階を分けて作る。
先の段階の機能は、前の段階が使える状態になってから着手する。

### 第1段階：マップ（MVP）

- 座標が確定したカードを、地図上にピンで表示する。
  座標が未確定のカードも、一覧と検索からは参照できる（「データの構成」を参照）。
- ピンは2種類に分ける。
  - **配布場所**：カードを受け取れる施設。
  - **蓋の位置**：カードに描かれたマンホール蓋が実際に設置されている場所。
- 蓋の位置は、カードに印刷された座標（代表の1か所）を表示する。
- カードを選ぶと、配布場所と蓋の位置の両方を地図上で示す。
- 1枚のカードに複数の配布場所がある場合（曜日によって場所が変わるなど）は、すべての場所を、その条件とともに示す。
- ピンの見た目で配布状態を区別する（「配布状態の扱い」を参照）。
- カードの詳細（自治体名、弾数、発行日、配布場所、配布時間、配布状態、公式の確認先、情報の最終確認日）を表示する。
- 現在地を表示し、近くのカードを探せる。
- 都道府県や市町村で地域を絞り込める。この機能は現在地なしで使える。
- 位置情報が拒否された場合や取得に失敗した場合は、前回見ていた範囲を表示する。初回は日本全体を表示する。
- ログインなしで、すべての機能を使える。

### 第2段階：ログインと回収記録

- ログインすると、回収記録を使えるようになる。
  記録はサーバーに保存し、複数の端末で同じ記録を見られる。
- 記録するのは、カードを回収したかどうかだけとする。
  このサービスの目的はカードを集めることであり、蓋を訪れたかどうかは記録しない。
- 記録はカード ID（「カードの識別」を参照）に結びつけ、データを取り込み直しても外れないようにする。
- 全体や地域ごとに、回収済みと残りの枚数を表示する。
  - 残りの枚数は、配布終了のカードも含めた全カードから数える。
  - 「配布中のカードだけ」に絞った残りの枚数も表示する。
- 地図上で、回収済みと未回収を見分けられる。

#### ログイン方式

- **パスキーのみ**でログインする。パスワードは扱わない。
  パスワードを保存しないので漏えいの対象がなく、パスキーは登録したサイトでしか使えないのでフィッシングにも強い。
- 必須の個人情報は持たない。メールアドレスの登録も求めない。
- 1つのアカウントに複数のパスキーを登録できる（スマホと PC など）。
- パスキーをすべて失ったときの復旧手段を用意する（方法は未決事項）。

### 第3段階：AI アシスタント連携

- MCP サーバーを提供し、ChatGPT や Claude などから、カードのデータを検索できるようにする。
- 想定する問い合わせ：
  - 「〇〇県で、まだ配布しているカードは？」
  - 「この旅程の近くで回れるカードは？」
- ログインしたユーザーなら、回収記録を踏まえて未回収のカードを提案できるようにする（任意）。

### 当面やらないこと

- 在庫状況の表示（GKP にも在庫データがないため）。
- 営業時間や休館日から「今この時間にもらえるか」を判定する機能。
- 背景地図のオフライン保存。
- ユーザーによる投稿機能（在庫切れの報告、写真の投稿など）。
- ネイティブアプリ（iOS、Android）。

## 配布状態の扱い

このサービスが示すのは「GKP の掲載情報の上で配布が続いているか」までであり、在庫の有無は示さない。
通常のピンが「今行けば必ずもらえる」と読まれないよう、詳細画面では配布状態と在庫を分けて表示する。

| 配布状態 | 意味 | 地図での表示 |
|---|---|---|
| **配布中** | GKP の掲載情報に、停止や終了の記載がない | 通常の色 |
| **一時中止** | 「一時中止」などの記載がある | 通常と区別できる表示（色や形は設計で決める） |
| **配布終了** | 「配布終了」の記載がある | グレー |
| **不明** | 記載が読み取れない、または矛盾している | 「要確認」の印をつける |

- **判定元**：GKP の表の記載から自動で判定し、誤りは手修正の上書きファイルで直す。
- **在庫**：どの配布状態でも「在庫は未確認」と表示し、公式の在庫確認先（GKP の表に載っているリンクや電話番号）へ案内する。

## データの構成

カードと配布場所は1対1ではない。
同じ施設で複数のカードを配る場合と、1枚のカードを曜日などの条件で別々の施設が配る場合の両方がある（2026年10月時点で、約400枚が後者に当たる）。
そのため、データは次の3つに分けて持つ。

- **カード**：ID、自治体名、弾数、発行日、配布状態、蓋の座標、公式の確認先、最終確認日。
- **配布場所**：施設名、住所、座標、電話番号。
- **カードと配布場所の対応**：どのカードを、どの場所で、どの条件（曜日など）で配るか。

座標が取れない場合は次のように扱う。

- 配布場所の座標が未確定でも、カードは一覧、検索、詳細に表示する。詳細では住所を文字で示し、「地図の位置は未確定」と表示する。
- 蓋の座標が読み取れない場合も同様に、蓋のピンを出さずにカードを表示する。
- 公開する時点では、配布中のカードの配布場所の座標をすべて確定させる（自動で取れないものは手で補う）。

## カードの識別

回収記録を保つため、データを取り込み直しても変わらない ID をカードに付ける。

- ID には、カードに印刷された公式のカード番号（例：`13-100-A001`）を使う。
- GKP の表の市町村欄にある記号（例：`A001`）と自治体コードから組み立てる。
  記号が載っていないカードは、カード画像に印刷された番号を読み取って補う。
  画像のファイル名は表記が統一されていないため、ID の根拠にはしない。
- カード番号が異なれば別のカードとして数える。
  同じカード番号の増刷や配布場所の変更は、同じカードとして扱う。
- 一度付けた ID は変えない。GKP 側の表記が変わっても、取り込み時に同じカードへ対応づける。

## 非機能要件

### 速さ

数値は仮置きであり、技術検証の結果を見て確定する。

| 場面 | 目標 |
|---|---|
| 初回起動（キャッシュなし） | 3 秒以内に完了 |
| 2回目以降の起動 | 1 秒以内に完了 |
| カードをタップしてから詳細が出るまで | 0.1 秒以内 |
| 地図の拡大縮小、移動 | 引っかかりなく動く |

起動の「完了」は、初期表示範囲の背景地図とピンが描画され、ピンをタップすると詳細が開ける状態を指す。
計測は次の条件で行う。

- **端末**：中価格帯の Android の実機1台と、Lighthouse のモバイル設定（中価格帯端末と低速 4G の模擬）。
- **回数**：各5回計測し、中央値で判定する。
- **初期表示範囲**：位置情報なしの初回起動（日本全体）で計測する。

### スマホでの使いやすさ

- スマホの縦画面を基準に設計する。PC でも使えるようにする。
- 片手で操作できる配置にする。
- ホーム画面に追加でき、アプリのように起動できる（PWA）。

### 通信がないとき

- 一度開いたことがあれば、通信がなくても、アプリの画面とカードのデータ（一覧、検索、詳細）を表示できることを保証する。
- 背景地図は、ブラウザに残っている範囲だけ表示される。表示を保証しない。

### 設計上の方針

- 地図とカードのデータの表示は、API サーバーの応答を待たない。
  カードのデータは静的ファイルとして配信し、ログインや回収記録だけを API で扱う。

## データの取得と更新

- **出典**：GKP「マンホールカード検索」ページ（全カードが1ページの表で取得できる）。公開 API はない。
- **配布場所の座標**：住所しか載っていないため、ジオコーディングで求める。
- **蓋の位置の座標**：カード画像の中にだけ印刷されているため、画像から文字を読み取って（OCR）求める。
- **手修正**：自動処理で誤った値は、上書き用のファイルで直す。上書きは取り込み直しても消えないようにする。

更新は、新しいカードの追加と、既存の情報の更新に分けて行う。

- **新しいカードの追加**：新しい弾の発行時（年3回、おおむね4月、8月、12月）に行う。座標の取得と確認を経てから公開する。
- **既存の情報の更新**：GKP のページを週1回取得し、前回との差分（配布場所、配布時間、配布状態の記載）を検出する。差分は人が確認してから公開する。
- **最終確認日**：カードごとに、GKP の掲載情報と一致を確認した日を持ち、詳細画面に表示する。
- **公式の確認先**：カードごとに、GKP の表に載っている確認先（自治体のページや電話番号）を持ち、詳細画面から案内する。
- **誤りに気づいた場合**：手修正の上書きファイルを直して公開し直す。手順は設計書に書く。

## 制約とリスク

- **カード画像の権利**：画像の著作権は GKP または自治体にあると考えられる。
  公開サービスで画像を表示する前に、GKP へ利用の可否を問い合わせる。
- **データの正確さ**：週1回の差分確認を挟んでも、GKP の掲載が実際の変更より遅れることがある。
  詳細画面に最終確認日と公式の確認先を示し、訪問前に公式情報を確認するよう案内する。
- **出典元への負荷**：一覧ページとカード画像で、取得の規則を分ける。
  - 一覧ページは、週1回の差分確認と弾の発行時に限って取得し、1回の取得は1リクエストで済ませる。
  - カード画像は、カード番号や蓋の座標を読み取るために、必要な画像だけを取得する。
    対象は、初回の取り込み、新しいカードの追加、一覧ページで画像の URL が変わったカードに限る。
  - 画像は1枚ずつ間隔を空けて取得し、取得した画像は手元に保存して再取得しない。
- **非公式であることの明示**：GKP 公式のサービスと誤解されない名前と表記にする。
- **パスキーの喪失**：OS をまたいだ機種変更や、パスキーの同期を切っていた場合に、ユーザーがすべてのパスキーを失いうる。
  パスワードもメールもないため、復旧手段を用意しないとアカウントに二度と入れなくなる。

## 未決事項

- サービス名。
- パスキーをすべて失ったときの復旧手段。
  候補は、登録時に発行するリカバリーコード（メール不要）と、任意で登録する復旧用メールアドレス。
- 同じデザインの蓋が自治体内に複数ある場合に、代表の1か所以外も表示するか。
  表示するなら、その座標をどこから集めるか。
- 一時中止のピンの見た目。
- ユーザーが誤りを知らせる窓口（問い合わせフォームなど）を設けるか。
- 収益化や運営費の扱い（地図タイルやサーバーの費用）。
