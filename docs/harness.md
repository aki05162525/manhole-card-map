# AIエージェントで開発するときのハーネス

AIに任せる作業の進め方と、そのための仕組みの改善点をまとめる。うまくいかなかったときは、担当の出来を責める前に、指示・検査・環境のどこを変えれば再発しないかを考えて、ここに足す。

作業の途中で気づいたら、そのPRか、次の小さなPRで更新する。作業ログや結果は書かず、次の作業で使う決まりと候補だけを書く。守る規則そのものは [AGENTS.md](../AGENTS.md)、レビューは [REVIEW.md](../REVIEW.md) に置く。

テスト・lint・フックで止められる規則は文書に書かず、仕組みに置く。文書には仕組みの場所と、機械では判定できない判断だけを書く。

| 止めているもの | 仕組み |
| --- | --- |
| フックのスキップ（`--no-verify`、`LEFTHOOK=0` など）、コミット署名の無効化、Git の恒久設定の変更 | `tools/agents/command_guard.py`。Claude Code は `.claude/settings.json`、Codex は `.codex/hooks.json` の PreToolUse から呼ぶ。Codex は `.codex/rules/` でも止める（Codex のフックは `/hooks` で信頼した後に動く） |
| `data/` への新しい実行コードと、取得した原本（`data/raw/`・`data/terms/` 以外への HTML・PDF・画像・タイルなど） | `tools/ci/data_policy.py`（pre-commit と CI）。原本の保存先は `tools/research/acquisition.py` も検査する |
| フロントエンド試験が参照する web 外のファイルの、CI の取得漏れ | `tools/ci/test_workflow_checkout.py` |
| 台帳の過去の位置の判断の書き換えと、判断を足さない施設の名称・住所の変更 | `tools/ci/ledger_history.py`（pre-commit と CI） |

## 役割

| 担当 | 役割 | 既定のモデル |
| --- | --- | --- |
| オーケストレーター | 設計の判断、指示、差分と報告の確認、統合、マージ | Claude Opus 5.5 |
| 設計・レビュー担当 | 実測と設計案、独立レビュー。リポジトリは変更しない | Codex Astra。設計レビューには Claude Fable 5.2 も使う |
| 実装担当 | 指示された範囲の実装とテスト、ブランチへのコミット | 仕様が明確なら Codex Sol（Claude の枠を使うなら Sonnet 5.5）、複雑なら Claude Opus 5.5。リファクタリングと見た目の作り込みは Claude Fable 5.2 |
| 並列の作業員 | 1つのコンテキストに収まらない調査・作業を分けて受け持つ | Claude Sonnet 5.5 か Codex Sol |
| 文書の簡潔化 | yomiyasu で推敲し、条件を落とさず短くする | Claude Haiku 5.5。下書きは Sonnet 5.5 |
| 読み取り担当 | 探索とログの読解。編集と判断はしない | Claude は `.claude/agents/`（Haiku 5.5）、Codex は `.codex/agents/`（Luna） |
| 利用者 | 目的と方針の判断、画面の確認 | — |

指揮は Claude Code が受け持つ。Claude の利用枠が尽きたときは、Codex の Astra が代わりに指揮する。

### 使い分けの軸

担当は次の順に決める。

1. 間違えたときの損失。データの正確さ・公開手順・資格情報は上位のモデルに任せ、別の系統にもレビューさせる。見た目はすぐ直せるので軽く扱う。
2. 仕様の明確さ。明確なら Sol か Sonnet、曖昧なものや設計を含むものは Opus か Fable。
3. コンテキストに収まるか。収まらない作業は Opus か Fable がリードし、並列の作業員に分ける。依存が一本につながる作業は分けない。
4. 系統。実装とレビューは別の系統にする（Claude が実装したら Codex、Codex が実装したら Claude）。
5. 利用枠。片方が詰まったら、もう片方の同じ格に替える（Opus と Astra、Sonnet と Sol）。

| 作業 | 担当 | レビュー |
| --- | --- | --- |
| 小さなバグ修正・UIの調整 | Sol（medium） | 見た目は利用者のプレビュー。データに関わるなら Claude Opus |
| 複雑な機能（アカウント、Worker の API など） | Opus（high） | Astra |
| 大規模なリファクタリング・設計 | Fable（medium） | Astra |
| 見た目の作り込み | Fable | 採点担当（Opus）と利用者の実機確認 |
| 都道府県ごとの位置候補の調査 | Opus がリードし、Sonnet か Sol を並列で動かす | Astra か Fable の独立レビュー |
| 文書 | Sonnet が下書きし、Haiku が簡潔にする | 意味が変わっていないかを Astra が見る |

Codex のモデルの評価は、モデル一覧の説明文とこのリポジトリでの経験に基づく。Claude のような公開の価格・ベンチマークで確かめたものではない。

### モデルと努力レベル

- 読むだけの作業（ファイルの探索、テスト・CIのログ、資料の要約）は読み取り担当に任せ、親のコンテキストを軽く保つ。任せるのは誤りに気づきやすい作業だけで、編集と判断は親に残す。Claude Code の組み込みの Explore と Codex の組み込みの explorer はセッションのモデルで動くため、同じ名前の定義で軽いモデルに替えている。失敗したCIは `ci-log-reader` に読ませる。
- 担当の力が足りないときは、次の順に上げる。
  1. 自己検証を指示に入れる（最初に失敗させるテスト、ビルド、確かめるコマンド）。
  2. 努力レベルを1段上げる。
  3. 上位のモデルに替え、努力レベルは下げ直す。Claude Opus を high より上げる前に Fable 5.2 を試す。
- 合否を機械で判定できる大量の作業（台帳の表の検査で落ちた項目、lint・型エラーの解消、件数の照合）は、まず low で全件を回し、失敗した分だけ high で再実行する。位置の採用、データの訂正、見た目の判断には使わない。
- モデルを替えるのは作業の区切りにする。キャッシュはモデルごとなので、全履歴を引き継がず、要約と指示書から始める。
- Codex を使う利点は次のとおり。
  - 利用枠が Claude と別。並列の実装や大量の読み取りを分けると、片方の上限で作業が止まりにくい。
  - モデルの系統が違うので、独立レビューで同じ系統の見落としを避けられる。Claude が実装した変更は Astra がレビューする。Sol が実装した変更のうち、データの正確さ・公開手順・資格情報に関わるものは Claude（Opus か Fable）にもレビューさせる。
  - `codex review --base main`（未コミットの変更は `--uncommitted`）で、差分を非対話でレビューできる。PR を作る前の一次確認に使える。

## 今の決まり

### 確認の重さ

- 外部ライブラリの開閉UIを拡張するときは、導入版が生成するDOMと開閉属性を実物で確認する。出典の常時表示では、狭い画面でもリンクの当たり判定と周辺操作が重ならないことを検査する。

- 共通の帯は自身でbox-sizing・行送り・最小高さを指定し、各ページの全体CSSに依存させない。帯の検査はリセットのない最小DOMとページ間の同じ幅で行い、帯の直下まで含めた遷移中のスナップショットも確認する。

- 文書ページの件数は配信データから生成し、データ差し替えとビルド出力の基準日を検査する。カスタム404はローカルの静的サーバーだけでなく、配信と同じWorkers Static Assetsでステータス・本文・既存HTMLの正規化を確認する。

- 空状態は見出しの個数に加え、0件の件数・内訳・基準日を重ねていないことを検査する。文字200%の確認は横あふれだけでなく、stickyな帯の高さ・アイコンの大きさ・件数の途中改行も確認する。

- 検査の重さは、失敗したときの損失に合わせる。
- デザインを段階的に作り込む作業では、段階ごとに、実装担当とは別の採点担当（Claude Opus）がスクリーンショットと実データの再現で採点表どおりに採点し、全軸8点以上で次へ進む。テストとlintが通っても、空の箱・重なり・語の途中の改行・重複表示は毎回この採点で見つかった。
- 確認の重さを分ける。実装担当はテストと変えた画面だけを撮る。ライトとダーク・PC・文字200%を含む全画面の採点は、採点担当が段階の最後に1回だけ行う。小さな修正のたびに全画面を撮らせると、作業が数時間に延びる。
- 一度直した問題が別の画面で再発したら、共通部品にまとめて直す。部品は各ページの全体CSSに依存させない。
- コントラストは目視でなく計算の検査をテストに置く。文字・操作の枠・装飾を分類して検査したことで、既存のライトの入力枠が基準を満たしていない不具合が見つかった。
- 利用者の実機での確認は、採点では見つからない使い勝手（スマホでの情報量）を拾う。段階の途中でも早めにプレビューを渡す。
- canvas上の帯は、DOMの当たり判定、影の解除、overflowとスクロール領域を別々に切り分ける。影だけで消えなければ、角丸の外枠と本文のスクロール領域を分けて確かめる。
- 色や影のトークンへの一括置換では、`none`・`transparent` などの意図的な例外を保持する。取っ手・パンくず・固定操作の背景など、例外のある規則を検査する。
- canvas上の円と文字は衝突判定が別になる。重なり0だけでなく、必要な地名がすべて表示され、自分の丸の隣にあること、数字が丸に収まることまで確認する。件数の最大値を入れた合成データでスマホ・PCの投影距離とラベルの当たりを検査し、出典は最長の詳細を開いた状態でも押せるか確かめる。
- 背景地図の配色を変える前に配信中の style JSON の source-layer を確かめる。同じ配信元でも OpenMapTiles と異なるスキーマがあるため、IDへの依存を避け、対応する小さなサンプルをテストに残す。
- シートの性能は操作開始・transform開始・終了をトレースへ記録し、移動中と終了後のレイアウト処理を分けて数える。終了後へ移した処理も含めて記録し、DOMテストでは履歴・余白の再計測・地図移動の順序を確認する。
- 地図の性能計測ではページだけでなくworkerのネットワークも記録・制限する。ページのCDPセッションで見えない取得を0バイトやキャッシュ命中と判断せず、圧縮サイズと実転送量を区別する。比較する計測の間に別のビルドやブラウザー試験を重ねない。
- 性能予算は対象チャンクと圧縮方式を明記する。ページ専用CSSとフォント宣言・地図ライブラリのCSSを別に集計し、外部CSSの増加も確認する。フォント名のチャンクにも共有トークンが混ざるため、ファイル名だけで全量をフォント宣言として除外しない。
- データ待ちの表示を最初の描画の内容に置き換えると、その配置計算（日本語の字形処理を含む）も最初の描画へ移り、FCPが遅れることがある。FCPと目的の表示の時刻を分けて測り、トレースの Layout で処理が移ったのか増えたのかを確かめる。
- 検索は住所や2番目以降の施設名による一致も検査し、検索対象に含まれる語が結果の行でも説明されることを確かめる。
- modal dialog の終了アニメーションは、裏の詳細が inert な間と解除後を分けてフォーカスを検査する。終了待ちには子要素の無限アニメーションを含めない。
- 通常の機能変更に伴う見た目の変更は、テスト・lint・型検査までを実装担当の合否にする。画面は利用者がプレビューURLで確認する。PR本文に確認してほしい点を書く。
- 公開手順、データの正確さ、資格情報が関わる変更は丁寧に確かめる。
- テストの期待値を書き換えて検査を通さない。
- 実装担当にスクリーンショットの網羅や計測を合否として課さない。ただし、見た目そのものを直す作業では、代表の画像を1〜2枚確かめると欠陥を早く見つけられる。
- 旧処理の仕組みや検査を新しい仕組みへ移す前に、それが守る実際の必要（誰が何に困るのを防ぐか）を一文で言えるか確かめる。言えなければ移さずに捨てる。言えるなら、最も単純な方法で満たす（旧処理と同じ方法とは限らない）。「旧処理と出力が一致する」「旧処理が拒否した入力を拒否する」を移行の合否にすると、旧処理の都合がそのまま新しい仕組みに残る。
- 独立レビューで前回の指摘の修正を確かめるときは、前回と同じ壊し方で再現させる。修正の確認が機械的になる。

### 指示の書き方

指示には次を書く。

- 目的と利用者の言葉
- 担当ファイル（並列のときは重ならないように）
- 判明済みの事実（再調査を減らす）
- 最初に失敗させるテスト
- 合否の条件
- 「全部終えてから報告する」「長いコマンドは前景で待つ」「コマンドで確かめた事実だけを書く」

「短く」のような抽象的な指示は効かない。何を削るかを読んでから具体的に書く。複数のPRで共有する仕様は、Issue など1つの文書にまとめる。

### 報告の扱い

- 報告はそのまま文書やPRに転記せず、実物で確かめる。
- 「成功」は実行した範囲でしか成り立たない。未接続・未実行・モックの範囲を分けて読む。
- 検査が通っても目的を満たすとは限らない。出力やデータの実物を1つ見る。

- 文字倍率別の検査分岐は定義だけで済ませず、通常のブラウザー検査から各倍率を呼び、computed font-size も確認する。

### 環境

- 配信の直後は、エッジの一部が少しのあいだ前の版を返す。配信後の確認（`web/scripts/smoke-deploy.mjs`）はコマンドとして実行したとき15秒おきに4回まで試し直す。同じ食い違いが続くときだけ本当の失敗として扱う。

- ローカルの実データ確認では、ブラウザーが受け取った基準日と生成JSONの基準日を照合する。過去の Service Worker が localhost の同じポートを制御している場合は、確認用オリジンの登録とキャッシュを除いてから再読み込みする。

- エージェント（Claude Code・Codex 共通）のコミットは、実行環境の `GIT_CONFIG_*`（`gpg.ssh.program=ssh-keygen`、`user.signingkey=~/.ssh/agent_signing.pub`）によりエージェント用の SSH 鍵で署名される。1Password の解除は不要。署名が失敗したら作業を残して利用者に伝える。
- Codex のフックは、端末で起動した CLI の `/hooks` で信頼する。T3 Code など app-server 経由の Codex では `/hooks` が通常のメッセージとして扱われ、信頼できない。信頼は `~/.codex` に記録され、T3 Code の Codex にも効く。`.codex/hooks.json` を変えたら信頼し直す。有効かどうかは、rules に一致しない無害な `echo hook-probe git commit -n .` が `Command blocked by PreToolUse hook` で止まるかで確かめる。
- コマンドのガードは、ヒアドキュメントの本文や `echo` の引数にある禁止の指定にも反応する。それらを含む文書を書き換えるときは、編集用のスクリプトをファイルに書いてから実行する。
- テストの `git` 呼び出しには `GIT_*` を渡さない。フックの環境の `GIT_DIR` で本体の `core.bare` が書き換わった例がある。
- 一時リポジトリでコミットするフックのテストは、コマンド単位で `-c commit.gpgsign=false` を付け、利用者の署名設定に依存させない。
- Sol には努力レベル medium を指定する。既定の low では途中で報告が返りやすい。
- 止まって見える担当でも再開することがある。代わりを起動する前に状態を確かめる。
- 新しいworktreeでは、最初に `python3 -B tools/dev/setup_checkout.py` を実行させる（依存、フック、スキル）。スキルの出力はGitの対象外なので、実行しないと読めない。
- PR を積み上げたら、下の PR がマージされた後に、上の PR の base を main へ変える。作業中の worktree のブランチは、マージされても作業が終わるまで片付けない。
- マージ後は `git fetch --prune` の後に `python3 -B tools/dev/clean_worktrees.py` で消す対象を確かめ、`--apply` で worktree とブランチを消す。未コミットの変更があるものや未マージのものは残る。

## これから作る仕組みの候補

上にあるものほど、効果が大きいと考えている。作ったら「今の決まり」へ移すか、この一覧から消す。

| 候補 | 困っていること | 作るもの |
| --- | --- | --- |
| 地図の撮影前の範囲復元 | viewportだけを変更すると、前のサイズで合わせたカメラが残り、全国の端を見切れとして誤判定する | 指定サイズへ変更してから全国画面を再読み込みし、9地方と沖縄が入る状態で撮影する |
| SVGアニメーションの完了状態 | 描画中だけ使う破線や非表示状態が終了後・reduced-motion時にも残ると、線の継ぎ目や欠落になる | 実ブラウザーで動きを許す場合と抑える場合の両方を検査し、終了後のdash・opacity・変形と要素ごとの開始時刻を照合する |
| 条件付きの色変更の事前検査 | ライト不変と両テーマのコントラスト条件が同時に課されると、既存の色の組み合わせが導入条件を満たさないことがある | ダークの実装・画像撮影の前に、現行CSSから文字・操作の枠・線画の組を取り出して比率を計算する。aria-hiddenの装飾と操作を識別する線を分け、入力ヒントのブラウザー既定の半透明色も確認する |
| 履歴イベントと再描画 | 先行するpopstateの処理が同期的に再描画すると、後続リスナーを付け直すeffectがそのイベントを取りこぼす | リスナーの購読を安定させ、先行リスナーで同期再描画する回帰テストと実ブラウザーの戻る操作で確認する |
| シートの実測と文字拡大 | 要約の高さを固定すると長い原文や文字拡大で主操作が隠れる | 代表の実データで本文とボタンの下端を測り、高さ上限・省略の分岐・状態変更後の再測定を同時に確認する |
| シートの遷移途中の検査 | 始点と終点だけでは、固定操作の往復移動や終了時の組み替えを検出できない | タッチとクリックの両方で遷移途中の矩形を採取し、固定列の絶対位置と要約のシートに対する相対位置を別々に比較する |
| UIの型の事前確認 | テストが通っても、操作の型が合わず公開後に作り直しになった | 大きなUIは実装前に、ワイヤーか試作で操作の流れを利用者に見せる手順 |
| 分担の実測 | 担当のモデルを、完了したタスクあたりの費用で比べていない | バックログの同じタスクを2つのモデルで実行し、`/usage` と差し戻しの回数を比べる。文書の簡潔化（Haiku と Sonnet 5.5）とリファクタリング（Fable と Opus の high）から始める |
| 委任の雛形 | 毎回長い指示を書き、注意事項の入れ忘れで差し戻しになる | 共通の注意事項をまとめた雛形（`AGENTS.md` への参照で済むものは削る） |
| 配信の差の確認 | Cloudflare の `/cards.html` から `/cards` への307がローカルでは再現せず、プレビューで初めて失敗した | 拡張子なしのパスをローカルの確認に含める |
| 実データのブラウザー確認 | 古い画面を前提にして失敗する状態に気づかなかった | 画面に合わせて更新し、手動で実行する機会を決める |
| fixtureのブラウザー検査 | CIで回さないため、`browser-check.mjs` が main で地図検索の空結果の文言を待って失敗していても気づかなかった（2026-11-10） | UIを変えるPRの前に手動で回すか、失敗を知らせる定期実行 |
| 画面の確認の案内 | 利用者が何を見ればいいかをPRごとに書いている | PR本文の確認項目の雛形 |
| 手元の依存の版ずれ | 依存更新のマージ後も手元の `web/node_modules` が古いままで、ローカルの検査が lockfile と違う版で通っていた（Vite 8.3.5 と 8.3.6） | 検査の前に `bun install --frozen-lockfile` を実行するか、版ずれを検出して知らせる仕組み |
| 未使用のCSSセレクタ | Knip はCSSのクラスを見ないため、要素を消した後の規則が残っていた | `src/**/*.css` のクラス・IDがソースに現れるかを照合する検査（`status-chip-${status}` のような組み立てる名前は除外する） |

UIの回帰テストでは、表示の文言だけでなくDOM順とリンク先を検査する。実データ用スクリプトのセレクタを更新するときは、状態バッジ・複数カード選択・外部経路URLを現在のコンポーネントと照合する。

統合後の見た目の検査では、条件付き要素を消した状態も含めてGridの列数と右端を実測する。浮動パネルは開閉の両方で隣接操作との重なりを検査し、CSS文字列の検査だけで完了にしない。

- 画面比較の撮影はフォントだけでなく一覧データ・地図描画の完了も確認する。読込中の画像を完成画面の比較根拠にせず、地図は各画面幅で再読込して初期カメラ条件を揃える。
