# AIエージェントで開発するときのハーネス

AIに任せる作業の進め方と、そのための仕組みの改善点をまとめる。うまくいかなかったときは、担当の出来を責める前に、指示・検査・環境のどこを変えれば再発しないかを考えて、ここに足す。

作業の途中で気づいたら、そのPRか、次の小さなPRで更新する。作業ログや結果は書かず、次の作業で使う決まりと候補だけを書く。守る規則そのものは [AGENTS.md](../AGENTS.md)、レビューは [REVIEW.md](../REVIEW.md) に置く。

## 役割

| 担当 | 役割 |
| --- | --- |
| オーケストレーター | 設計の判断、指示、差分と報告の確認、統合、マージ |
| 設計担当（Astra） | 実測と設計案、独立レビュー。リポジトリは変更しない |
| 実装担当（Sol） | 指示された範囲の実装とテスト、ブランチへのコミット |
| 利用者 | 目的と方針の判断、画面の確認 |

## 今の決まり

### 確認の重さ

- 共通の帯は自身でbox-sizing・行送り・最小高さを指定し、各ページの全体CSSに依存させない。帯の検査はリセットのない最小DOMとページ間の同じ幅で行い、帯の直下まで含めた遷移中のスナップショットも確認する。

- 文書ページの件数は配信データから生成し、データ差し替えとビルド出力の基準日を検査する。カスタム404はローカルの静的サーバーだけでなく、配信と同じWorkers Static Assetsでステータス・本文・既存HTMLの正規化を確認する。

- 空状態は見出しの個数に加え、0件の件数・内訳・基準日を重ねていないことを検査する。文字200%の確認は横あふれだけでなく、stickyな帯の高さ・アイコンの大きさ・件数の途中改行も確認する。

- 検査の重さは、失敗したときの損失に合わせる。
- 色や影のトークンへの一括置換では、`none`・`transparent` などの意図的な例外を保持する。取っ手・パンくず・固定操作の背景など、例外のある規則を検査する。
- canvas上の円と文字は衝突判定が別になる。重なり0だけでなく、必要な地名がすべて表示され、自分の丸の隣にあること、数字が丸に収まることまで確認する。件数の最大値を入れた合成データでスマホ・PCの投影距離とラベルの当たりを検査し、出典は最長の詳細を開いた状態でも押せるか確かめる。
- 背景地図の配色を変える前に配信中の style JSON の source-layer を確かめる。同じ配信元でも OpenMapTiles と異なるスキーマがあるため、IDへの依存を避け、対応する小さなサンプルをテストに残す。
- 性能予算は対象チャンクと圧縮方式を明記する。ページ専用CSSとフォント宣言・地図ライブラリのCSSを別に集計し、外部CSSの増加も確認する。フォント名のチャンクにも共有トークンが混ざるため、ファイル名だけで全量をフォント宣言として除外しない。
- 検索は住所や2番目以降の施設名による一致も検査し、検索対象に含まれる語が結果の行でも説明されることを確かめる。
- modal dialog の終了アニメーションは、裏の詳細が inert な間と解除後を分けてフォーカスを検査する。終了待ちには子要素の無限アニメーションを含めない。
- 見た目の変更は、テスト・lint・型検査までを実装担当の合否にする。画面は利用者がプレビューURLで確認する。PR本文に確認してほしい点を書く。
- 公開手順、データの正確さ、資格情報が関わる変更は丁寧に確かめる。
- 実装担当にスクリーンショットの網羅や計測を合否として課さない。ただし、見た目そのものを直す作業では、代表の画像を1〜2枚確かめると欠陥を早く見つけられる。

### 指示の書き方

指示には次を書く。

- 目的と利用者の言葉
- 担当ファイル（並列のときは重ならないように）
- 判明済みの事実（再調査を減らす）
- 最初に失敗させるテスト
- 合否の条件
- 「全部終えてから報告する」「長いコマンドは前景で待つ」「コマンドで確かめた事実だけを書く」

「短く」のような抽象的な指示は効かない。何を削るかを読んでから具体的に書く。複数のPRで共有する仕様は1つの文書にまとめる。

### 報告の扱い

- 報告はそのまま文書やPRに転記せず、実物で確かめる。
- 「成功」は実行した範囲でしか成り立たない。未接続・未実行・モックの範囲を分けて読む。
- 検査が通っても目的を満たすとは限らない。出力やデータの実物を1つ見る。

### 環境

- ローカルの実データ確認では、ブラウザーが受け取った基準日と生成JSONの基準日を照合する。過去の Service Worker が localhost の同じポートを制御している場合は、確認用オリジンの登録とキャッシュを除いてから再読み込みする。

- コミットの署名を無効にしない。署名が失敗したら作業を残して利用者に解除を頼む。
- テストの `git` 呼び出しには `GIT_*` を渡さない。フックの環境の `GIT_DIR` で本体の `core.bare` が書き換わった例がある。
- 一時リポジトリでコミットするフックのテストは、コマンド単位で `-c commit.gpgsign=false` を付け、利用者の署名設定に依存させない。Git の恒久設定は変えない。
- 努力レベルは、実装担当には中程度を指定する。既定では途中で報告が返りやすい。
- 止まって見える担当でも再開することがある。代わりを起動する前に状態を確かめる。
- 新しいworktreeでは、最初に `python3 -B tools/dev/setup_checkout.py` を実行させる（依存、フック、スキル）。スキルの出力はGitの対象外なので、実行しないと読めない。
- マージ後は、worktreeと作業ブランチを削除する。自動では消えない。消す前に未コミットの変更を確かめる。

## これから作る仕組みの候補

上にあるものほど、効果が大きいと考えている。作ったら「今の決まり」へ移すか、この一覧から消す。

| 候補 | 困っていること | 作るもの |
| --- | --- | --- |
| 条件付きの色変更の事前検査 | ライト不変と両テーマのコントラスト条件が同時に課されると、既存の色の組み合わせが導入条件を満たさないことがある | ダークの実装・画像撮影の前に、現行CSSから文字・操作の枠・線画の組を取り出して比率を計算する。aria-hiddenの装飾と操作を識別する線を分け、入力ヒントのブラウザー既定の半透明色も確認する |
| 署名の事前確認 | 長い作業の最後に署名の失敗で止まる。繰り返し起きている | 作業の開始時に署名できるかを確かめる手順 |
| UIの型の事前確認 | テストが通っても、操作の型が合わず公開後に作り直しになった | 大きなUIは実装前に、ワイヤーか試作で操作の流れを利用者に見せる手順 |
| worktreeの掃除 | 手で消し忘れて大量にたまる | マージ済みで変更のないworktreeとブランチを消すスクリプト |
| 委任の雛形 | 毎回長い指示を書き、注意事項の入れ忘れで差し戻しになる | 共通の注意事項をまとめた雛形（`AGENTS.md` への参照で済むものは削る） |
| 共有の仕様の置き場 | 複数のPRで使う仕様を一時ディレクトリに置いていて、消えると追えない | PRやIssueに置く運用 |
| 配信の差の確認 | Cloudflare の `/cards.html` から `/cards` への307がローカルでは再現せず、プレビューで初めて失敗した | 拡張子なしのパスをローカルの確認に含める |
| 実データのブラウザー確認 | 古い画面を前提にして失敗する状態に気づかなかった | 画面に合わせて更新し、手動で実行する機会を決める |
| 参照閉包の検査 | `evidence_graph.py` が手動で、参照切れが増えても気づけない | 増えたときだけ失敗するCI検査 |
| 画面の確認の案内 | 利用者が何を見ればいいかをPRごとに書いている | PR本文の確認項目の雛形 |
