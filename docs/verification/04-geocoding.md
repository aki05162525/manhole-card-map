# 技術検証 4：配布場所の住所からの座標取得

実施日：2026-10-21
対象：GKP 一覧（2026-10-21 版）の北海道、東京都、長野県、大阪府、鹿児島県の配布場所

## 目的

自由記述の住所から、配布場所の座標をどこまで自動で求められるかを確かめる。
デジタル庁の abr-geocoder v2.3.1 とアドレス・ベース・レジストリ（ABR）を使う。
国土地理院の住所検索 API は、利用条件を確認できていないため採用しない。
今回得た座標は候補であり、公開用の確定データではない。

## 対象と入力の整形

`cmd/addresses` が抽出した住所は、重複を除いて 356 件だった。
出どころは 312 枚のカードに属する 430 件で、同じ住所でもカードや窓口が違えば別の出どころとして残す。
住所のない場所は今回の入力に入っておらず、対象の全配布場所を処理できたという意味ではない。

都道府県名がない住所には、カードの都道府県名を補った。
住所中の空白を整理し、数字以外の文字と半角数字の間にある空白を除いた。
閉じ括弧が開き括弧より多い場合は、末尾の半角閉じ括弧を1個除いた。
元の住所、カードの行番号、配布場所名、住所を隣の場所から借りたかどうかは `addresses-sources.json` に保存する。
誤字や町名を手で直す処理は加えていない。

## 再現手順

リポジトリのルートで実行する。
以下の `S` は今回の作業場所であり、別の環境では書き込み可能な作業場所に置き換える。
シェルによる引数分割をそろえるため、ダウンロードのコード列挙はコンテナ内の `sh` で行う。

```sh
S=/tmp/claude-1000/-home-akihiro-personal/e7197be4-9ecc-44f7-b1ff-a5f00443705a/scratchpad/abrg
go run ./cmd/addresses -list data/raw/gkp-list-20261021.html -pref 01,13,20,27,46 -out data/work/addresses.txt
cp data/work/addresses.txt "$S/addresses.txt"

# 新しい環境でのみ必要。今回の node_modules はインストール済み。
docker run --rm -v "$S:/w" -w /w node:22 npm install @digital-go-jp/abr-geocoder@2.3.1

# 比較元。5都道府県を1回で指定する。
docker run --rm -v "$S:/w" -w /w node:22 node node_modules/@digital-go-jp/abr-geocoder/build/interface/cli/cli.js download -d /w/data -t 1 --silent -c 130001 270008 200000 460001 010006
docker run --rm -v "$S:/w" -w /w node:22 node node_modules/@digital-go-jp/abr-geocoder/build/interface/cli/cli.js /w/addresses.txt /w/geocoded.json -d /w/data -f json --silent
cp "$S/geocoded.json" data/work/geocoded.json

# 比較元が返したコードを重複なく列挙する。
python3 - "$S" <<'PY'
import json, pathlib, sys
s = pathlib.Path(sys.argv[1])
rows = json.loads((s / 'geocoded.json').read_text())
codes = sorted({r['result']['lg_code'] for r in rows if r['result']['lg_code']})
(s / 'codes.txt').write_text('\n'.join(codes) + '\n')
PY

# data と混ぜず、新しいディレクトリに取得する。
docker run --rm -v "$S:/w" -w /w node:22 sh -c 'node node_modules/@digital-go-jp/abr-geocoder/build/interface/cli/cli.js download -d /w/data-c -t 1 --silent -c $(cat /w/codes.txt)'
docker run --rm -v "$S:/w" -w /w node:22 node node_modules/@digital-go-jp/abr-geocoder/build/interface/cli/cli.js /w/addresses.txt /w/geocoded-c.json -d /w/data-c -f json --silent
cp "$S/geocoded-c.json" data/work/geocoded-c.json

# 技術検証 3 の ocr.json も必要。
python3 docs/verification/geocoding-summary.py > data/work/geocoding-summary.txt
```

Node 24 では依存する uWebSockets.js が動かず、`node:22-slim` にはインストールに必要な git がないため、`node:22` を使った。
インストール済みパッケージの `package.json` で v2.3.1 を確認した。
Docker が作ったファイルの変更や削除が必要な場合は、同じボリュームをマウントしたコンテナ内で行う。
今回は既存データを削除せず、再計算を別のファイルに保存した。
`data/work/` の結果はコミットしない。

## データの取得で起きた問題

前段の試行では、都道府県コードを複数指定して既定の並列数で取得すると `SQLITE_BUSY` が起きた。
`-t 1` で5都道府県を1回の実行にまとめると、ジオコーディングまで進んだ。
一方、都道府県ごとの取得を同じディレクトリに重ねたデータでは、`getCityList` から `reading 'pref'` の例外が出た。
これらの例外の再現実行は今回繰り返していない。

5都道府県をまとめた `data`（約 9.1 GB）には、住居表示の ZIP があっても `rsdt_blk` と `rsdt_dsp` がなかった。
新宿区だけを指定した先行試行では、街区 1,679 行、住居番号 29,359 行が入っていた。
この違いから、コードを個別に列挙して別ディレクトリ `data-c` に取得した結果を調べた。

引き継ぎ時の「187 市区町村コード」は、正確には市区町村コード 186 件と大阪府のコード `270008` の計 187 件だった。
大阪狭山市の誤字を含む入力が都道府県止まりになり、その結果をコード列挙に含めていた。
186 市区町村すべてのデータベースファイルが存在した。
大阪府コードによる取得範囲も含むため、`data-c` の city テーブルは 218 行ある。
ジオコーディング結果から取得範囲を決める方法は、誤った照合結果も引き継ぐ点に注意が要る。

今回確認した時点では実行中の Docker コンテナはなく、ダウンロードのログは空だった。
背景処理の終了コードは取得できていないが、住居表示テーブルの読み取りと 356 件の再計算は正常終了した。
再ダウンロードは行わなかった。

| テーブル | data の行数 | data-c の行数 | data-c で1行以上ある DB 数 |
|---|---|---|---|
| rsdt_blk（街区） | テーブルなし | 159,591 | 75 |
| rsdt_dsp（住居番号） | テーブルなし | 2,980,562 | 71 |
| parcel（地番） | 30,468,375 | 20,891,548 | 216 |
| town（町字） | 77,753 | 60,240 | 1 |

件数はコンテナ内の `better-sqlite3` で、各 SQLite ファイルを読み取り専用で開き、各テーブルに `SELECT count(*)` を実行して合算した。
すべての自治体に住居表示があるとは限らないため、住居表示テーブルがないことだけでは欠落と判定しない。
配信元の全 CSV とデータベースの全行照合までは行っていない。

## 集計

### 座標の段階

文字列の一致段階 `match_level` ではなく、返された座標の段階 `coordinate_level` を数えた。
両方の結果が同じ 356 住所を一度ずつ含むことを集計スクリプトで検査した。

| coordinate_level | data | data-c |
|---|---|---|
| residential_detail（住居番号） | 0 | 95 |
| residential_block（街区） | 0 | 20 |
| parcel（地番） | 102 | 89 |
| machiaza_detail（丁目や小字） | 165 | 69 |
| machiaza（町字） | 80 | 74 |
| city（市区町村） | 8 | 8 |
| prefecture（都道府県） | 1 | 1 |
| 座標なし | 0 | 0 |
| 合計 | 356 | 356 |

座標が変わったのは 115 件で、すべて住居番号または街区の段階に変わった。
内訳は `machiaza_detail` から 96 件、`machiaza` から 6 件、`parcel` から 13 件である。
細かな段階の座標が出たことだけでは、その施設を指すと確定できない。

### 蓋の座標からの距離

`addresses-sources.json` の出どころ1件を、行番号で `ocr.json` のカード1枚に結びつけた。
同じ住所の別窓口も別に数え、住所だけでは重複を除かなかった。
430 組のうち、新宿区 O001（行 443）と藤井寺市 B001（行 950）は `ocr.json` の座標がないため除外し、428 組を集計した。
上書きファイルを直接読み直す処理は加えていない。
引き継ぎの集計は 427 組だったが、現在の保存ファイルとこの集計方法では 428 組となる。
差の1組を過去の処理までさかのぼって特定できていないため、比較元も今回の方法で再集計した。

半径 6,371 km の球面距離を使った。
中央値は中央の2値の平均、90% 点は昇順で `ceil(0.9 × 件数)` 番目とした。

| 指標 | data | data-c |
|---|---|---|
| 中央値 | 0.52 km | 0.50 km |
| 90% 点 | 3.83 km | 3.87 km |
| 最大 | 20.34 km | 20.34 km |
| 20 km 超 | 1 組 | 1 組 |

20 km を超えたのは、両方とも大阪狭山市の大阪府立狭山池博物館（行 957）だった。
配布場所と蓋は別の場所であるため、この距離は測位誤差ではない。
90% 点が増えたことも、ジオコーディングの精度低下を意味しない。

### 有名な場所との比較

比較用の点を固定して、前後の結果からの距離を求めた。
建物や案内所の代表点との比較であり、入口や窓口を測量した正解データではない。
比較点を配布場所の座標として採用する補正は行っていない。

都庁の比較点は[東京都の統計の FAQ](https://www.toukei.metro.tokyo.lg.jp/faq/fq-faq.htm)の度分秒を十進度に変換した。
大阪は[大阪観光局の案内ページ](https://osaka-info.jp/spot/tourist-information-osaka/)の埋め込み地図の `q` 座標を使った。
京成上野は[東京都の観光公式サイト](https://www.gotokyo.org/jp/plan/tourist-info-center/)から案内される[地図リンク](https://goo.gl/maps/PvmJuUArFEbSpJvg6)の地点座標（`!3d` と `!4d`）を使った。
地図表示の中心座標（`@` 以下）は使っていない。
引き継ぎの概算（都庁はほぼ一致、大阪約 300 m、京成上野約 450 m）と同じ傾向で、京成上野では住居表示の読み込みによる改善が見られた。

### 入力の整形で扱った問題

北区の `志茂 5-41-1` は、町名と番地の間に空白があった。

空白の削除は住所の書き方への対応、閉じ括弧の削除は一覧の余分な記号への対応である。

したがって、今回の前後差はこのコード修正の効果を測ったものではない。

## 利用条件

収益化を基本的に行わないサービスを前提に確認した。
非営利であることによる出典記載の免除はなく、以下の条件を満たす必要がある。

### abr-geocoder と ABR

abr-geocoder のプログラムは MIT ライセンスである。
プログラムを複製、再配布する場合のライセンス表示と、座標の元データの出典表示は別に扱う。

[ABR の利用規約](https://www.digital.go.jp/policies/base_registry_address_tos)は、原則として[公共データ利用規約 PDL1.0](https://www.digital.go.jp/resources/open_data/public_data_license_v1.0)を適用する。
複製、公衆送信、加工、商用利用が認められるが、出典を記載し、加工した場合は加工の事実と主体を出典とは別に明示する。
加工した結果をデジタル庁が作った未加工の情報のように示さない。
地番マスターと地番マスター位置参照を利用すると、登記所備付地図データ利用規約にも同意したものとみなされる。

### 登記所備付地図データ

G空間情報センターの[規約掲載ページ](https://www.geospatial.jp/ckan/dataset/houmusyouchizu-riyoukiyaku/resource/47871bf1-4c85-48f7-a8fe-b27c6643c1c5)から配信される[原本 PDF](https://www.geospatial.jp/ckan/dataset/fc3b0593-ce9e-40d1-aa33-94382d5f0da1/resource/47871bf1-4c85-48f7-a8fe-b27c6643c1c5/download/license.pdf)の全2ページを確認した。
ブラウザー取得は 403 だったが、カタログ API で配信 URL を確認し、curl で原本を取得できた。
規約に記された制定日は 2023-01-23 である。

- 冒頭で複製、公衆送信、加工を認め、商用利用も認めている。加工した座標を静的ファイルで配る場合も、出典と加工の表示を付ける方針とする。
- 1）で出典記載を求める。例にはデータ名、法務省、対象ページの URL、利用日が含まれる。加工した場合はその事実を別に記し、国が作成した情報と誤認させない。
- 2）と3）に利用制限と禁止行為がある。法令違反、不正利用、サービス妨害、他の情報との照合による個人の識別、第三者の財産やプライバシーの侵害などを禁じる。
- 5）と6）に免責とデータの限界がある。作成時期によって精度が異なり、現在使われない市区町村名が含まれる場合がある。

この本文には、再配布について別途許諾を申請する条件や、同じライセンスでの公開を義務づける条項は見当たらなかった。
本サービスでは施設の位置を示すために使い、個人の識別には使わない。

### 出典表記の案

サービスの出典ページに以下を記載し、座標を配る静的データにも出典ページへの参照を残す案とする。
角括弧の部分は公開前に実際の名称と URL に置き換える。
ABR の利用規約 URL だけでなく、実際に利用したデータの掲載ページを記録する。

```text
出典：アドレス・ベース・レジストリ（デジタル庁）
      ［使用したマスターと位置参照データの掲載ページ URL］
      PDL1.0、2026年10月21日利用
出典：登記所備付地図データ［対象市区町村名］（法務省、G空間情報センター）
      ［対象データセットの掲載ページ URL］、2026年10月21日利用

加工：［本サービスの運営者名］が、上記データを用い、abr-geocoder v2.3.1 により
      配布場所の住所から座標候補を作成した。

```

利用日は今回の検証用の値であり、公開用データを作り直す際は実際の日付に置き換える。

## 限界と未確認の点

- 5都道府県の 356 住所に限った検証であり、全国の住所で同じ結果が出るとは確認していない。
- 住居表示データの読み込みは確認したが、対象自治体の全データが完全にそろったことは証明していない。
- ABR の配信データは更新される。v2.3.1 を固定しても、後日のダウンロードで同じ件数や座標になるとは限らない。
- 町字や丁目の代表点は、施設への経路案内に使うには粗い場合がある。大阪駅では約 283 m の差が残った。
- 地番や住居番号の段階でも、住所の誤記、元データの誤り、別施設の住所の借用を排除できない。
- 蓋からの距離と3地点の比較だけでは、全施設の座標の正しさを確定できない。
- 市区町村止まりの住所には、書き方の問題とデータ収録の問題が混在しうる。原因未確定のものを一覧の誤りとして修正しない。
