# 技術検証 6：地図の試作と描画方式の比較

実施日：2026-10-21〜2026-10-22
対象：保存済み一覧の全1,313枚と、技術検証4の5都道府県の配布場所

## 目的

日本全体の背景地図とピンを表示し、詳細を開けるまでの時間を比較する。
Leaflet と地理院のラスタタイルを案A、MapLibre GL JS と自前配信の PMTiles を案Bとする。
画面、カードデータ、詳細表示、オフライン保存、初期表示の指定範囲は共通にした。
試作を外部公開するデプロイは行わず、`127.0.0.1:4173` だけで配信した。
カード画像を使わず、GKP にアクセスせず、上書きファイルと要件定義を変更していない。

## 比較する構成

| 項目 | A | B |
|---|---|---|
| 地図 | Leaflet 1.9.4 | MapLibre GL JS 6.15.0 |
| 背景 | 地理院の標準地図 `std` | Protomaps 2026-10-20 版を切り出した PMTiles |
| ピンの集約 | leaflet.markercluster 1.5.3 | GeoJSON source の cluster |
| ベクトル地図の読み出し | 該当なし | pmtiles 4.5.0 の HTTP Range |
| スタイル | 標準地図の画像 | @protomaps/basemaps 5.7.2 の light、日本語優先 |
| 背景の配信先 | 地理院のサーバー | ローカルサーバー。フォントとアイコンも同じオリジン |

Vite 8.3.5 と TypeScript 7.0.2 を使い、UI フレームワークは使わない。
検証時の依存関係は pnpm 10.33.2 と `web/pnpm-lock.yaml` で固定した。
現在の開発基盤は Bun と `web/bun.lock` に移行している。以下の計測記録は当時のもので、
現行のセットアップ手順と CI 用 fixture の制限は [web/README.md](../../web/README.md) を参照する。
A と B を動的に読み分け、初回の起動完了までに他方の描画ライブラリを要求しない。
Service Worker の保存は起動完了後に始め、両方の画面を保存する。

B は東経122〜154度、北緯20〜46度の外接矩形と交差するタイルを、ズーム0〜15で切り出した。
国境で地物を切り抜いたものではなく、矩形内の近隣国と、低ズームのタイルに含まれる周辺地域も残る。
初期表示は両案とも同じ矩形を画面に収めるが、Leaflet は整数ズーム、MapLibre は小数ズームなので、実際に見える周辺範囲は完全には一致しない。
B はズーム15より上を拡大表示し、A は標準地図のズーム18までを使う。
近接時の地図の細かさが同じという比較ではない。

PMTiles は3,737,849,910 bytesだった。
SHA-256 は `ffe53b1be0ee26a2289f02c5bc4619959afd6e5cc203e29a5a7e1fe0e0f26797` で、`pmtiles verify` を通した。
切り出しに使った go-pmtiles は1.31.2である。
全ファイルをブラウザへ配るのではなく、索引と必要なタイルだけを部分取得する。
事前確認用のズーム0〜10版も作ったが、比較の測定には使っていない。

## 配布データの形

`cmd/builddata` は、保存済み一覧と `data/work/municheck.json` を読み、技術検証5が採用した番号と座標を引き継ぐ。
その前提として、一覧、OCR、上書き、ジオコーディング、住所の出どころの SHA-256 が、照合結果に記録されたものと一致するか検査する。
入力が変わっていれば停止し、古い自治体照合を新しいデータへ流用しない。
上書きの根拠、確認者、確認日も詳細に保持する。

| 配列 | 主な項目 | 対応 |
|---|---|---|
| `cards` | 印字番号の `id`、自治体、弾、発行日、配布状態、蓋、確認先、取得日、上書き記録 | 1,313枚 |
| `places` | `id`、施設名、住所、電話、座標の状態と採用元 | 1,680件 |
| `relations` | `cardId`、`placeId`、曜日条件、原文、期間原文、代替案内原文、代替元、住所借用 | 1,725件 |
| `pins` | `id`、関連カードID、種類、配布状態、座標、参考位置かどうか | 1,309件 |

カードのIDに行番号や画像名を使わず、検証済みの印字番号を使う。
配布場所は都道府県、施設名、住所、電話、住所借用の有無が一致するものをまとめ、そのキーのハッシュをIDにする。
同じ住所だけでは別施設をまとめない。
座標の精度や確認状態は場所IDに含めない。
施設名や住所そのものを訂正した場合の場所IDの引き継ぎ台帳は本番実装に残るが、回収記録を結び付けるカードIDには影響しない。

全都道府県の配布場所の文字情報を保持するが、座標候補があるのは検証4の5都道府県だけである。
配布条件は既存パーサーの結果を保持し、一覧の原文もカードと対応に残す。
期間の曖昧な表現を日付に直さない。
`alternativeTo` は通常の場所のIDを持てる nullable な項目としたが、今回のパーサーでは対応先を確定できないため null のまま残す。
期間と代替先の案内は原文で表示できるが、場所ごとの厳密な構造化は未完了である。

配布状態は `active`、`upcoming`、`suspended`、`ended`、`unknown` の5値である。
終了と再開が同時にあるなど矛盾を検出した場合は `unknown` にする。
開始予定の表記と取得日より後の発行日も扱う。
今回の保存済み一覧では配布中1,210枚、一時中止96枚、配布終了7枚となった。
これは掲載情報からの暫定判定で、在庫の判定ではない。
詳細にはどの状態でも「在庫は未確認」と示す。

### 確定状態とピンの対象

座標には `confirmed`、`candidate`、`unconfirmed` を持たせる。
蓋の `confirmed` は、既存の検証で印字の読み取りを採用した状態を指し、現地で測量したという意味ではない。
人の確認とAIの確認、自動照合は `review` で区別する。

宇都宮市 C001、藤井寺市 B001、砥部町の3枚はピンから外した。
加えて、検証5で自治体不一致の原因が未確定だった胎内市 A001 も外した。
この4枚も一覧から選び、文字情報を読める。
三鷹市の境界付近の点は印字の読み取りとして残し、現地位置の確認済みとは扱わない。

配布場所は、人による施設位置の確定がまだない。
場所のうち208件が参考表示の条件を満たす候補で、残る1,472件は取得範囲外や借用住所、粗い座標などである。
そのため既定の出力と今回の速度測定では配布場所のピンは0件である。
「未確定の座標にはピンを出さない」という条件を優先したため、実データで2種類のピンを同時に表示する検証は未完了である。
参考位置を試作だけに表示してよいかは、人の判断に残る。

表示用の実装は両種類を持つ。
`-reference-places` を付けた生成では、借用住所でなく、自治体名での照合が一致し、座標の段階が住居番号、街区、地番のいずれかである候補だけを、参考ピンへ出せる。
既定の出力ではこの機能を使わない。
町字や丁目の代表点も施設を示すには粗いと判断し、参考ピンの対象から外す。
借用住所50件と、検証4の市区町村や都道府県止まりの9住所は、自治体一致を理由に復活させない。

### 一括と分割

`full.json` はカード、場所、対応、ピンをまとめたファイルである。
比較用に、ピンだけの `pins.json` と残りの `details.json` も出力する。
`manifest.json` にはデータの日付、入力と出力のハッシュ、参考ピンの有無を記録する。
今回の生成では一括と分割を両方保存し、容量も測った。

| ファイル | 非圧縮 bytes | gzip bytes | Brotli bytes |
|---|---:|---:|---:|
| `full.json` | 2,749,148 | 449,062 | 223,915 |
| `pins.json` | 193,016 | 21,601 | 17,073 |
| `details.json` | 2,556,262 | 427,092 | 213,186 |

gzip は level 9、Brotli は quality 11 である。
以下はビルド成果物の容量であり、HTTPヘッダーは含まない。

| JS/CSSの構成 | 非圧縮 bytes | gzip bytes | Brotli bytes |
|---|---:|---:|---:|
| AのJS（共通込み） | 192,693 | 55,991 | 48,504 |
| BのJS（共通とWorker込み） | 1,652,733 | 453,350 | 371,084 |
| AのCSS（共通込み） | 17,415 | 7,214 | 6,351 |
| BのCSS（共通込み） | 72,969 | 10,807 | 8,792 |

分割版も、ピンをタップしたときに追加通信を待たないよう、起動時にピンと全詳細を並列取得する。
ピンだけが出た時点を起動完了とはしない。
詳細を後から取る方式は、初回タップを0.1秒以内に返す条件と、オフラインで詳細まで使う条件を別に満たす必要があるため、今回の比較に含めていない。
本番では採用した一方だけを配信できる。

## 画面とオフライン保存

蓋は丸、配布場所は四角にし、配布状態で色を変える。
終了は灰色、複数カードの配布状態が混在する場所は要確認の色にする。
ピンを選ぶと関連カードの詳細を示し、そのカードに関連する表示可能なピンを強調して画面に収める。
同じ場所の複数カードは詳細へまとめて表示できる。
詳細を開くと地図の高さを縮め、地図と詳細を上下に並べる。
詳細が選択したピンや出典表示を覆わない配置とした。
合成した2枚のカードと1か所の配布場所で、両種類のピン、複数カードの関係、詳細、位置情報拒否、前回の範囲の復元を確認した。
合成データは操作検査の通信だけで差し替え、保存済みのカードデータには書き込まない。

一覧と検索は座標のないカードも含む。
現在地はボタンを押したときだけ要求する。
失敗時は表示中の範囲を使い、通常起動では前回の範囲を復元し、前回がなければ日本全体を表示する。
計測用の `benchmark` パラメーターでは前回の範囲を復元しない。

Service Worker はビルド内容のハッシュごとにキャッシュを分け、アプリの HTML、JS、CSS とカードデータを全部保存してから有効になる。
全ファイルの存在を確認した場合だけ「オフライン準備完了」と保存データの日付を表示する。
背景タイル、PMTiles、地図のフォントとアイコンはこの保存対象に含めない。
初回の保存失敗や、端末による保存データの削除後は、オフライン表示の保証対象にならない。

保存完了後に通信を切り、両案で全カードの一覧と詳細を表示できることを自動操作で確認した。
この確認は背景地図の表示保証を意味しない。
バージョン更新中のタブの競合、保存容量の不足、OSによるキャッシュ削除は未検証である。

## 再現手順

保存済みの入力を用意し、リポジトリのルートで実行する。
技術検証3〜5の処理を最初から再実行する必要はない。
背景地図が保存済みなら、取得スクリプトは再取得しない。

```sh
go run ./cmd/builddata
bash web/scripts/fetch-map.sh
cd web
pnpm install --frozen-lockfile
pnpm build
pnpm preview
```

ブラウザで `http://localhost:4173/?engine=a` または `http://localhost:4173/?engine=b` を開く。
サーバーはループバックだけで待ち受ける。
`pnpm build` は JS、CSS、カードデータを事前に gzip と Brotli で圧縮する。
JS、CSS、カードデータの配信時には圧縮処理を行わない。
地図用フォントとアイコンはサーバーの最初の要求で圧縮し、以後はメモリ上の応答を再利用する。

地図用アセットは `protomaps/basemaps-assets` のコミット `028c18f713baecad011301ff7a69acc39bcc2ae7` に固定した。
大きなファイル、生成データ、依存パッケージ、生のトレースは `.gitignore` の対象である。
`dist/maps` はローカルの背景地図を参照するシンボリックリンクで、配信用成果物として外部にアップロードしない。

サーバーを動かしたまま、別の端末で次を順番に実行する。
同時実行するとCPUや回線を奪い合うため、比較に使わない。

```sh
cd web
pnpm sizes
node scripts/measure.mjs
node scripts/lighthouse.mjs
node scripts/interaction.mjs
node scripts/verify.mjs
node scripts/summarize.mjs
```

生の結果は `web/results/` に保存する。
今回の記録は削除せず、このローカルディレクトリに残した。
画面修正前の結果は `before-final-layout/`、準備処理と重なった除外トレースは `excluded-compression-overlap/` に区別した。
Chrome の場所は `CHROME`、回数は `RUNS` で変更できる。
既定の回数は5である。
提出用の集計と各回の数値は `docs/verification/06-results.json` に保存する。

## 測定の条件

| 項目 | 条件 |
|---|---|
| ホスト | WSL2、Linux 6.18.54.1、AMD Ryzen 9 7940HS、16論理CPU、メモリ約14 GiB |
| ブラウザ | Google Chrome 150.0.7871.46、headless |
| 画面 | 412 × 823 CSS px、deviceScaleFactor 1.75、モバイル、位置情報なし |
| ビルド | `pnpm build` の production 出力 |
| Chrome の通信制限 | 待ち時間150 ms、下り1.6 Mbps、上り750 kbps |
| Chrome のCPU制限 | 4倍の低速化 |
| 回数 | A/Bそれぞれ初回5回、再起動5回。一括と分割も別に測定 |
| 初回 | 新しいブラウザプロセスと一時プロファイル。HTTPキャッシュとService Workerなし |
| 再起動 | 同じプロファイルで、Service Workerの保存完了後に同じページへ再遷移 |

ブラウザを冷たく起動する条件を作っているが、OSのファイルキャッシュ、ローカルサーバーの応答キャッシュ、地理院のCDNキャッシュは消していない。
画面修正前の予備測定は集計に含めず、最終ビルドの5回を使う。
容量の集計処理と重なったAの1組は除外し、同じ条件で測り直した。
再起動はキャッシュが有効な直後の測定であり、数日後やキャッシュ削除後まで1秒を保証するものではない。
ローカル配信にもブラウザの通信制限を適用するが、公開先のTLS接続、DNS、CDN、回線の揺れを再現する測定ではない。

ChromeのSystemInfoで、描画先はANGLEのVulkan経由のSwiftShaderと確認した。
MapLibre はこの環境のソフトウェア描画経路で動く。
スマホのGPU性能を4倍に遅くした測定ではなく、実機のWebGL性能と同一視できない。
この制約は特にBの拡大縮小の結果に影響する。

Lighthouse 13.5.0 はモバイル設定を使い、`throttlingMethod: devtools` を指定した。
既定のシミュレーションは独自の起動完了マークを低速回線に換算しないため、実際に制限を掛けたページでマークを採るための指定である。
CPUは4倍、ネットワークはLighthouseの `mobileSlow4G` の値を使い、Chrome側の150 ms設定とは別の測定として扱う。
Lighthouseの実際の通信制限値はrequestLatency 562.5 ms、下り1,474.56 Kbps、上り675 Kbpsである。
各初回に新しいブラウザプロファイルを作るため、Lighthouse自身のストレージ削除は無効にした。
Lighthouseの既定処理は測定終了時にもService Workerを消すため、再起動用の保存を残すための指定である。
Lighthouseのタップ測定は監査終了後の同じページでCPUと回線の制限を適用し直して行い、Chrome測定の起動直後のタップとは実施時点を区別する。
スコアやLCPだけでは背景地図とピンの完成を判定しない。

### 起動とタップの計測点

起動完了は `performance.mark('map-ready')` で記録する。
詳細データがメモリにあり、一覧と操作イベントを取り付け、次の条件が成立した後、2回の `requestAnimationFrame` を経て記録する。

- A：ピンの集約を地図に取り付け、初期範囲のタイルの `load` が終わっている。
- B：ピンのsourceとlayerを取り付けた後に `idle` となり、`areTilesLoaded()` が真である。

背景地図の取得エラーを検出した場合は起動完了にしない。
2回のフレーム待ちはブラウザ内の描画機会を含めるための近似で、物理ディスプレイの発光時刻を測るものではない。
画面のスクリーンショットでも地図とピンを確認した。

タップは、実際に表示されている集約されていないピンをChromeの入力機能でクリックする。
クリックイベントの時刻から、詳細のDOM更新と2回のフレーム待ちまでを `pin-to-detail` として測る。
処理の関数を直接呼んだ時間ではないが、物理的な指の接触からクリック成立までの時間は含まない。
各描画ライブラリが返す非集約ピンの先頭を使うため、AとBで同じカードに固定した測定ではない。
詳細の文字量の差も含み、配布場所が多いカードや全カードの最悪値は未確認である。

| A / 再起動 | 6 | 0 | 0 |
| B / 初回 | 15 | 575,292 | 6 |
| B / 再起動 | 15 | 242,559 | 6 |

Aは6枚のタイル、BはPMTilesの6回の部分取得にフォント7件とアイコン2件が加わった。
Bの再起動ではフォントとアイコンはキャッシュに残ったが、PMTilesの部分取得は再び通信した。
Range応答がこのローカルサーバーとChromeの組み合わせで再利用されなかった観測であり、PMTiles形式全般でキャッシュが不可能という意味ではない。
Workerの転送完了がページのCDPセッションに通知されない場合があるため、ページ全体の通信総量は確定値として出さず、JS/CSSの容量はビルド成果物から別に集計した。
保存完了のために起動後に行うService Workerの通信は、この表には含めていない。

### 移動と拡大縮小

再起動後に東京周辺へ移動し、ズーム10と11の切り替えとパンを6組行った。
最終版は各案1回のトレースを保存し、Chrome Performanceで扱う `PipelineReporter` のフレーム状態を集計した。
`STATE_DROPPED` を、全描画、部分描画、脱落の合計で割った割合を使い、更新なしのフレームは分母から除いた。
併せて `requestAnimationFrame` の間隔を記録した。
フレーム脱落とコールバックの遅れは異なる指標なので、別々に示す。

| 案 | 脱落率（1回） | 33.4 ms超のフレーム間隔の回数（1回） | 最大フレーム間隔 ms（1回） |
|---|---:|---:|---:|
| A | 3.3% | 0 | 33.3 |
| B | 42.7% | 79 | 216.7 |

追加計測を終えるという利用者の指示により、フレーム計測は各案1回で終了した。
5回の中央値ではなく参考値であり、画面修正前の予備測定を補って回数をそろえてはいない。
Aでも脱落を記録したため、「引っかかりがない」とは判定しない。
Bはこのソフトウェア描画環境では脱落と長いフレーム間隔が多かった。
GPUを使うAndroid実機で同じ差が出るかは未確認である。
生のトレースをDevToolsのPerformanceへ読み込み、Frames、Main、GPUの時間軸を確認できる。
各回のフレーム状態とトレースのSHA-256は集計JSONに残した。

## 利用条件と費用

### A：地理院タイル

[地理院タイルの利用案内](https://maps.gsi.go.jp/help/use.html)では、ウェブサイトやアプリでリアルタイムに読み込む利用は、出典の明示で申請不要とされている。
画面には「地理院タイル」と[地理院タイル一覧](https://maps.gsi.go.jp/development/ichiran.html)へのリンクを表示した。
[国土地理院コンテンツ利用規約](https://www.gsi.go.jp/kikakuchousei/kikakuchousei40182.html)の原則はPDL1.0で、加工する場合は出典とは別に加工の事実も示す必要がある。
第三者の権利や個別法令による例外は、使うタイルごとに確認する。

[地理院地図の利用規約](https://maps.gsi.go.jp/help/termsofuse.html)は、正常運用を妨げる程度の負荷を与える通信に対し、予告なく遮断する場合があると定める。
この規約から「何件までなら必ず使える」という上限やSLAは読み取れない。
試作では表示と測定に必要なタイルだけを取り、全国の画像の一括取得やService Workerへの保存は行っていない。
実際に利用者が増えた段階で通信量を確認し、大量アクセスを無制限に受け入れてもらえる前提にしない。
タイルの従量課金は今回確認した案内にないが、アプリ本体の配信費用は別にかかる。

### B：PMTilesとOpenStreetMap

[OpenStreetMapの著作権ページ](https://www.openstreetmap.org/copyright)は、提供者の表示とODbLへの案内を求める。
画面に `© OpenStreetMap contributors` と著作権ページへのリンクを常時表示した。
[Protomapsのデータライセンス](https://github.com/protomaps/basemaps/blob/main/LICENSE_DATA.md)に従い、海岸線由来のデータ、Natural Earth、landcoverで使うESA WorldCoverも区別した。
画面にProtomaps、Natural Earth、ESA WorldCoverへのリンクを併記し、プログラムと素材のライセンス本文を `web/THIRD_PARTY_BASEMAPS.md` と `web/THIRD_PARTY_DATA.md` に保存した。
地図用フォントのOFLも取得ファイルに含まれる。

[Protomapsの説明](https://github.com/protomaps/basemaps/blob/main/README.md)ではタイルセットをOSMのProduced Workとして扱う。
公開時は、出典表記だけでなく、実際に配るタイルと加工元の区別、ODbLの適用範囲を確認する。
独立して取得したカード情報は別のファイルに保ち、OSMの地物へ混ぜて編集していない。
Bの費用見積もりは、公開先の契約や設定を行ったものではない。

[Cloudflare R2の料金表](https://developers.cloudflare.com/r2/pricing/)を例に、Standard storageで試算する。
単価は保存が月1 GB当たり0.015米ドル、Class Bの読み取りが100万回当たり0.36米ドル、外向き転送は無料である。
無料枠は保存10 GB-month、Class Aが100万回、Class Bが1,000万回である。
同じアカウントの他用途との合計と、請求単位の切り上げに注意する。

今回の3.74 GBを1か月保存すると、無料枠を使わない場合は4 GBに切り上げて約0.06米ドルになる。
更新時に新旧2版を保持しても約7.48 GBであり、他用途がなければ保存の無料枠内に収まる。
月1万回の初回起動を仮定すると、PMTilesだけで約6万GET、初期表示の部分取得は約2.4 GBとなる。
フォントとアイコンまで全件がオリジンへ届く保守的な仮定では約15万GETである。
この規模はClass Bの無料枠内で、無料枠を除いた最初の100万回の請求単位は0.36米ドルとなる。

これは起動時だけの試算である。
移動や拡大の回数、タイルの更新、CDNキャッシュ、アップロードのClass A操作、ドメイン、アプリとカードデータの配信費は別に数える。
R2へ直接Range配信する想定であり、WorkerによるタイルAPIを挟む費用は含めない。
単価を円へ換算せず、課金契約やデプロイも行っていない。

## 採用の推奨

MVPの実装ベースにはAを推奨し、カードデータは一括読み込みを採る。
このデータ件数ではAのJSが小さく、背景地図の初回通信も少なく、再起動では画像キャッシュを使えている。
一括版は分割版の合計よりBrotliで6,344 bytes小さく、Chromeの初回起動もA/Bの両方で一括版の中央値が短かった。
一括と分割の数十msの差を他環境でも保証できるとは扱わないが、今回の条件では分割を採る速さの根拠がない。

ただし、Aも初回3秒の目標は満たしていない。
タップもChromeの起動直後の中央値が約101 msで、100 msの基準をわずかに超えた。
「Aを採れば要件を満たした」という結論にはしない。
数値目標を変更せず、初回の背景画像とカードデータの量、解析処理、詳細を開く際の地図移動を改善する対象とする。

Bの自前配信は配信先とデータの更新を管理できるが、今回の初期表示ではJSとフォントを含む取得量、部分取得の往復が増えた。
ソフトウェア描画による不利もあるため、Android実機のGPUでの比較は残る。
その確認前にBの滑らかさの一般的な優劣までは確定しない。
OpenLayersなどの別案を今回の2案より明らかに有利と判断できる実測根拠は得ておらず、追加実装はしていない。

## 限界と未確認の点

- Android実機での測定は未実施である。
  要件の合格判定は実機でも満たす必要があり、今回だけで合格にしない。
- 配布場所は未確定のため、実データの速度測定は蓋1,309ピンだけである。
  2種類のピンを含む性能の確定には、参考表示を認めるか座標を確定してから再測定する必要がある。
- 5都道府県以外の配布場所の座標はない。
  公開条件である「配布中カードの配布場所をすべて確定」は満たしていない。
- 場所ごとの期間と代替元の厳密な構造化は未完了で、原文を残している。
  今日どの施設で配布するかは判定しない。
- 状態判定は保存済み一覧の文言に基づく。
  複数施設の一部だけの中止など、文章の意味の範囲まで自動で確定していない。
- 日本周辺の矩形で切り出しているため、近隣国のタイルも含む。
  日本の陸域に沿った切り出しで容量がどこまで減るかは未測定である。
- BのRange配信はローカルHTTPである。
  公開先のキャッシュ、ETag、CORS、Rangeの扱いによって通信量は変わる。
- CPUの4倍低速化は特定のAndroid端末のCPUやGPUの再現ではない。
  特にWebGLの比較には実機が必要である。
- アプリ更新時の複数タブ、保存領域不足、キャッシュ削除は未検証である。
  比較用に両エンジンと一括版と分割版を保存するため、最小の本番キャッシュではない。
- パッケージのインストールではLighthouseの間接依存にOpenTelemetryのpeer dependency警告が出た。
  今回のLighthouse実行結果とは分け、将来の更新時に解消を確認する。

## Android実機での測定手順

1. 中価格帯のAndroidを1台決め、機種、SoC、メモリ、AndroidとChromeの版、画面サイズ、電池残量、端末温度を記録する。
   充電と発熱の条件を5回でそろえる。
2. USBデバッグを有効にし、PCのChromeの `chrome://inspect/#devices` で接続する。
   ポート転送で端末の `localhost:4173` をPCの `127.0.0.1:4173` へ向け、外部にデプロイしない。
3. `?engine=a&benchmark` と `?engine=b&benchmark` を使う。
   位置情報は許可せず、初期範囲を日本全体にする。
   端末の実CPUを測るので、CPU4倍の追加制限は掛けない。
4. リモートDevToolsのNetworkで低速4Gを設定する。
   待ち時間、下り、上りの実際の設定値を記録し、両案で同じ値にする。
5. 初回はApplicationのClear storageでService WorkerとCache Storageを消し、HTTPキャッシュも消す。
   Performanceの記録を開始して再読み込みし、`map-ready` までを測る。
   Disable cacheは再起動の測定前に必ず解除する。
6. 「オフライン準備完了」を待ち、キャッシュを消さずに再読み込みする。
   再起動の `map-ready` を測り、初回との組を5回作る。
   A/Bを交互に実施する。
7. 両案で同じカードの集約されていないピンをタップし、`pin-to-detail` を5回測る。
   初回起動後と再起動後を分け、中央値を出す。
8. 東京周辺でズーム10と11の切り替えと移動を同じ順序で行い、PerformanceのFramesとMain、GPUの記録を保存する。
   赤く表示される落ちたフレーム、50 msを超える処理、操作中の背景の欠落も記録する。
9. Networkの転送量をJS/CSS、カードデータ、背景地図に分ける。
   BはPMTilesだけでなく、フォントとアイコンも背景に含める。
   Rangeが206で返り、毎回全ファイルを取っていないことも確かめる。
10. 保存完了後に機内モードにして、再起動、一覧検索、未確定カードの詳細を確認する。
    背景地図が消える場合も、一覧と詳細が使えるかを別に判定する。

報告には各回の値と中央値を残す。
初回3秒、再起動1秒、タップ0.1秒の基準を実機とLighthouseの両方で満たしたかを判定し、中央値だけで目立つ遅延を隠さないよう最大値も併記する。
