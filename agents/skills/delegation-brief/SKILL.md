# 委任の指示とレビューの往復

担当に渡るのは指示の本文だけで、この会話の履歴は渡らない。雛形を写して `<…>` を埋め、当てはまらない行は消す。どの担当とモデルに任せるか、独立レビューに出すかどうかは [docs/harness.md](../../../docs/harness.md) の「役割」と「確認の重さ」に従う。

## 雛形を選ぶ

| 頼むこと | 雛形 |
| --- | --- |
| 新しい PR を作る実装 | [templates/implement.md](templates/implement.md) |
| 開いている PR に修正を足す | [templates/amend-pr.md](templates/amend-pr.md) |
| PR の独立レビュー | [templates/review.md](templates/review.md) |
| 前回の指摘が直ったかだけを確かめる | [templates/recheck.md](templates/recheck.md) |

レビューと再確認も含め、どれも別の checkout で動かす（delegate_task なら `isolation: "worktree"`）。checkout を共有したまま「リポジトリを変更しない」と頼むと、担当は試しのファイルを作業ディレクトリの外に作り、Codex はそのたびに承認を求める。

## 指示に書くこと

雛形の空欄は次の考え方で埋める。

- 目的と利用者の言葉。利用者の言葉は言い換えずに引く。
- 担当ファイル。並列で進めるときは、並行する PR が触るファイルも挙げて重ならないようにする。
- 判明済みの事実（調べた範囲、捨てた案とその理由）。複数の PR で共有する仕様は Issue など1つの文書にまとめ、指示ではそこを指す。
- 守らせる条件は、利用者が決めた見た目・決まりと安全の条件に限る。前からある実装・規則・文書を、理由を言えないまま「変えない」と固定しない。良くなるなら作り直してよいと書く。
- 「短く」「きれいに」のような抽象的な指示は効かない。対象を読んでから、何を削るか・何を合否にするかを具体的に書く。
- lint・テスト・フックで止まる決まりは、指示で繰り返さない。「〜に気をつける」と書くのは、仕組みで止められないものだけにする。

作業の進め方と報告の形（前景で待つ、`pipefail`、全部終えてから報告する、最後の行）は各雛形に書いてある。消さずに残す。

## 報告を受け取ったら

- 報告をそのまま文書や PR に写さず、実物（差分、コマンドの出力、データ）で確かめる。「成功」は実行した範囲でしか成り立たない。実行していない範囲とモックの範囲を分けて読む。
- 検査が通っても目的を満たすとは限らない。出力やデータの実物を1つ見る。
- 止まって見える担当でも再開することがある。代わりを起動する前に状態を確かめる。

## レビューの往復

- 指摘を直した後は、指揮役が差分を読んで判断する。もう一度レビューに出すのは、修正が指示から外れているときと、認証の仕組みそのものを変えたときに限る。出すときは [templates/recheck.md](templates/recheck.md) を使い、前回の指摘を前回と同じ壊し方で再現させる。
- 2回目のレビューでも同じ種類の指摘（到着順、持ち主、すり抜け方の別の例）が続くなら、1件ずつ直させる指示をやめる。原因の設計（何を持ち主として結び付けるか、どこで正規化するか）を整理させてから直させる。[templates/amend-pr.md](templates/amend-pr.md) の「設計の整理」を使う。次のレビューでは個別の例を探させるより、その整理の筋が通っているかを見させる（[templates/review.md](templates/review.md) の該当行）。
