# 実装（新しい PR）の雛形

`<…>` を埋め、当てはまらない行は消す。

````markdown
リポジトリ manhole-card-map（main 起点の worktree、<起点の SHA> 以降）で、<作ること・直すこと> の PR を作ってほしい。

## 目的
<何を、なぜ。関係する Issue・PR の番号>

利用者の言葉:
> <言い換えずに引く>

## 範囲
- 担当ファイル: <パス>
- 並行して別の PR が触るファイル（この PR では変えない）: <PR の番号とパス>
- 判明済みの事実: <調べた結果、捨てた案とその理由>
- 守る条件: <利用者が決めた見た目・決まり、安全の条件だけ>。前からある実装・文書も、良くなるなら作り直してよい。

## 進め方
1. 最初に `python3 -B tools/dev/setup_checkout.py` を実行する。<実データが要るとき: `web/public/data/` は Git 管理外なので、<元の checkout のパス> からコピーする>
2. 変える振る舞いが今のコードで失敗するテストを先に書き、失敗することを確かめる: <テストの場所と、確かめる振る舞い>。自明なテストは書かない。
3. 実装する。
4. 合否のコマンドを通す（触った範囲のものを残す）:
   - `web/`: `bun run lint && bun run lint:css && bun run knip && bun run format:check` と `bun run typecheck && bun run test && bun run build:fixture`
   - ルート: `go test -count=1 ./...`
   - ルート: `python3 -B -m unittest discover -s tools/ci`、`python3 -B -m unittest discover -s tools/dev`、`python3 -B -m unittest discover -s tools/agents`
   計測、スクリーンショットの網羅、main との操作の比較は合否に入れない。
5. ブランチ `<ブランチ名>` にコミットして push し、`gh pr create --base main` で PR を作る。本文は日本語で、目的、変えたこと、最初に失敗したテスト、実行した検証と未確認の範囲、<画面が変わるとき: 利用者にプレビューで確かめてほしい点> を書く。マージはしない。

## 作業の決まり
- PR 本文は構造化引数で渡す。CLI を使うときは本文ファイルを編集ツールで用意し、`gh pr create` または `gh pr edit` を `--body-file <パス>` 付きで単独実行する。本文の作成や削除を同じシェル呼び出しに含めると、コマンド全体の承認を求められることがある。
- 長いコマンドは前景で待つ。バックグラウンドに回したまま報告を返さない。
- 出力を `tail` などで絞るときは `set -o pipefail` を付けるか、ログに保存してから読む。表示用のコマンドの成功で、検証の失敗を隠さない。
- 負荷のせいで変更と無関係のテストが時間切れになったら、負荷が下がってから同じコマンドを再実行する。期待値や timeout を変えて通さない。
- 全部終えてから報告する。

## 報告
- コマンドで確かめた事実だけを書く。実行したコマンドと結果を書き、実行していない検証は分けて書く。
- 文書とコードの食い違いを見つけたら、すべて挙げる。
- 最後の行は `PR <URL>, head <SHA>` にする。
````
